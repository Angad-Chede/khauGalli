2. Detailed Walkthrough of Built Features (Phases 0–2)

Phase 0: Foundations, Infrastructure & Auth Guardrails

  • Monorepo Topology: Configured using pnpm workspaces and Turborepo (apps/api, apps/web, apps/worker, packages/db, packages/shared).
  • Zod Environment Validation: packages/shared/src/env.ts enforces strict runtime checks and crashes on boot in production if demo flags, default JWT secret, or mock Razorpay keys are used.
  • HMAC-SHA256 OTP Auth: 6-digit random code hashed using crypto.createHmac('sha256', secret) and stored in Redis with 5-minute TTL. Rate limited to 3 requests per 10 minutes. Fixed demo code (123456) is strictly restricted to the 4 seeded demo phones and blocked in production.
  • Demo Persona Switcher: Floating bar enables instant persona switching. Each switch executes real OTP authentication under the hood.
  • Idempotent Seed Engine: packages/db/src/seed.ts marks seeded users as is_demo: true with safe numbers (+919999900001–0004). The notification layer intercepts and drops these so external SMS/WhatsApp adapters never message real people.

Phase 1: Catalog & Customer Browse

  • Pure Pricing Package (@tiffin/shared/pricing): Features text-based rupee parser (parseRupeesToPaise) eliminating JavaScript floating-point errors (e.g. 0.57 * 100 = 56.99999999999999). Computes distance-based delivery fee (₹30.00 base for 2 km + ₹10.00/started km, capped at ₹150.00), 5% food GST, and 15-minute immutable quotes (calculateCartQuote). Verified across 1,000 property-based iterations via fast-check.
  • PostGIS Spatial Discovery (GET /restaurants): PostGIS ST_DWithin and ST_Distance queries calculate geodesic distance from customer coordinates, verify service zone polygon containment, evaluate Asia/Kolkata operating hours, and calculate dynamic ETAs.
  • Multi-Tier Search (GET /restaurants/search): Uses prefix matching (< 4 chars) combined with Postgres Full-Text Search (tsvector with simple dictionary) and Trigram similarity (word_similarity) for typo tolerance (e.g. "briyani" matches "Biryani Darbar").
  • Redis Cart & Multi-Restaurant Conflict: Ephemeral Redis cart strictly enforces the single-restaurant invariant (HTTP 409 RESTAURANT_CONFLICT). Validates modifier group min/max selection constraints.
  • Staff-Scoped Restaurant Portal (/r/*): Restaurant ID is derived server-side from the restaurant_staff table using req.user.sub to prevent IDOR. Staff can toggle operational status and instant 86-availability, bumping menu_version.

Phase 2: Orders, Payments, State Machine & Kitchen KDS

  • Order State Machine (packages/shared/src/state-machine.ts): Enforces deterministic transitions (CREATED → PAYMENT_PENDING → PLACED → ACCEPTED → PREPARING → READY → PICKED_UP → DELIVERED) and terminal exits (PAYMENT_FAILED, REJECTED_BY_RESTAURANT, EXPIRED, CANCELLED). Prevents illegal jumps.
  • Idempotent Placement (POST /orders): Enforces Idempotency-Key header. Retried requests return the existing order with isReplay: true and zero duplicate DB rows.
  • Price Shift Detection (HTTP 409 PRICE_CHANGED): Re-verifies live prices and taxes against PostgreSQL. If prices shifted or quote is older than 15 minutes, aborts with HTTP 409 returning the refreshed quote.
  • Raw Body Webhook Engine (POST /webhooks/razorpay): Uses custom Fastify content-type parser to preserve unaltered raw buffers. Performs timing-safe HMAC-SHA256 verification, deduplicates events via webhook_events, and prevents out-of-order state regression (captured payment cannot be downgraded to authorized).
  • Auto-Expiration Engine: 3-minute kitchen acceptance window. Unaccepted orders in PLACED auto-transition to EXPIRED and trigger full refunds.
  • Transactional Outbox Relay Worker (apps/worker): Background daemon uses SELECT ... FOR UPDATE SKIP LOCKED on outbox_events to publish events to Redis Pub/Sub channels (restaurant:{id}:orders, order:{id}:updates).
  • Live Kitchen Display System (KDS): 3-column Kanban board in /restaurant with Web Audio alert chime, live 3-minute countdown timers, and touch-friendly accept/reject/ready controls.
  • Live Order Tracker: Customer tracking page (/customer/orders/:id) with 5-stage visual progress stepper, cancellation button, and auto-refresh.

3. Real-Time Events vs Client Polling (Technical Clarification)

How updates currently reach the browser: Currently, the tracking page (/customer/orders/:id) and kitchen board (/restaurant) use client HTTP polling (setInterval(fetchOrders, 3000)). While the background worker successfully relays events from outbox_events into Redis Pub/Sub, a browser cannot connect to Redis Pub/Sub directly.

Phase 3 Gateway Plan: Phase 3 will build an SSE (Server-Sent Events) or WebSocket gateway in the API that subscribes to Redis Pub/Sub and pushes messages down to authenticated browser connections.

Fire-and-Forget Reconnect Requirement: Because Redis Pub/Sub is fire-and-forget (at-most-once delivery), clients that disconnect or lose cellular coverage will miss published events. Therefore, on reconnection, clients must always issue an HTTP catchup fetch (e.g. GET /orders/:id) to synchronize state against PostgreSQL (system of record).

The codebase currently defaults to rzp_test_mock_key_id for automated CI and local headless execution without external dependencies. However, the cryptographic HMAC verification logic in apps/api/src/lib/razorpay.ts and /webhooks/razorpay is production-ready.

Wiring Real Razorpay Sandbox Keys for Demo Evaluation:
  1. Sign up for a free Razorpay account at dashboard.razorpay.com and switch to Test Mode.
  2. Generate a Test Key ID and Key Secret from Settings → API Keys.
  3. In your .env file, set: 
    RAZORPAY_KEY_ID=rzp_test_YOUR_KEY_HERE
RAZORPAY_KEY_SECRET=YOUR_SECRET_HERE
RAZORPAY_WEBHOOK_SECRET=YOUR_WEBHOOK_SECRET_HERE
  4. Expose your local Fastify API via tunnel (e.g. Cloudflare Tunnel or ngrok) and configure the webhook URL in Razorpay Dashboard pointing to https://your-tunnel/webhooks/razorpay.

5. Concurrency Race Conditions & Edge Cases Verified

The test suite in apps/api/test/order-race-conditions.test.ts directly proves the following concurrency failure modes:

  • Kitchen Accept vs Worker Auto-Expire Race: When the kitchen lead taps "Accept" at the exact same millisecond the background worker triggers 3-minute auto-expiry, the first transition commits via row-level lock; the second transition is rejected with a state machine conflict error. Both cannot win.
  • Late Webhook Arrival After Expiry: If a customer's bank capture webhook arrives after the 3-minute acceptance window has elapsed and the order is already in terminal EXPIRED status, the state machine strictly refuses transition to PLACED. The webhook engine catches this and triggers an automated refund.
  • Refund Failure Retries: If a payment gateway refund call encounters a transient 503 or timeout, the task is retained in PENDING status and retried with exponential backoff until successfully processed.
  • Demo User Notification Guard: Proves that any notification directed to seeded numbers (+919999900001–0004) or records with is_demo: true is intercepted and dropped, never reaching external cellular SMS or WhatsApp networks.

6. Tax Treatment Assumptions & Disclaimer

Tax Treatment Notice: The platform models a 5% GST on prepared restaurant food based on Section 9(5) of the Indian CGST Act (where e-commerce operators like Swiggy/Zomato pay GST on restaurant services).

Disclaimer: The tax treatment of the Delivery Partner Fee and Platform Fee (whether bundled under restaurant composite supply or subject to 18% GST under SAC 9985/9968) is a working demo assumption and is explicitly labeled as unverified pending formal validation by a Chartered Accountant.
